## 2. 应用接入与服务选配

**适用人员：**平台管理员。**目标：**让每个产品线及其 iOS/Android 应用拥有明确的服务范围和执行配置。

操作顺序：

1. 在配置管理中维护产品线、成员角色和服务资源。
2. 从“应用接入”维护应用系统、包标识、项目标识及平台专属配置。
3. 在目标应用的“选配服务”中选择模块；Sentry/Bugly 可选一个主崩溃提供商，也可都不启用。
4. 配置对应资源，再查看配置缺项或接入状态。
5. 切换顶部产品线和应用，核对页面及 AI 工具是否符合已选范围。

规则与边界：

- 质检依赖 Jenkins 和真机服务；启用质检补选依赖，取消依赖会取消质检，后端也校验组合。
- Android 只启用 Jenkins 时，仅要求 APK 构建配置，不强制 Smoke Job 和设备配置。
- 关闭服务保留历史证据及资源配置，不会自动终止外部已运行任务，也不修改 Jenkins Job 脚本。
- 显式关闭全部服务后重启不会自动恢复默认服务。
- Bugly 支持保存 App ID/控制台 URL；Android Sentry 同样只具备控制台配置层能力，不能当作已有问题同步。
- 共用组件库允许同系统产品线共享组件版本、Nexus/Specs 资源；主工程配置仍独立。

主要接口：`GET /api/auth/application-services`、`GET/POST /api/auth/product-lines/:id/applications`、`PATCH /api/auth/product-lines/:id/applications/:applicationId`、`GET/PUT /api/auth/product-lines/:id/services`。

### 2.1 应用身份与配置边界

每条产品线当前每种系统接入一个应用。应用的系统、应用 ID、`projectId` 是隔离身份，执行配置可编辑；不要用修改身份的方式切换历史归属。显式服务列表 `[]` 表示全部停用；旧数据的空值保留兼容默认，新建初始 iOS 应用不会因此自动启用全部服务。代理访问、AI 确认执行与后台同步分别检查服务选配。

Jenkins 服务地址和凭据在产品线层共享，Android 使用独立 Job 与执行配置。提供商控制台 URL 不等于 Sentry API 地址；仓库 URL 和控制台 URL 不存放凭据。物理设备、部分 API 定义与 OP 会话、平台访问统计等存在共享基础设施，不能把所有数据都视为按产品线独占。

<a id="permissions"></a>

### 2.2 成员与发布授权

管理员按产品线维护成员角色。研发的 App Store 发布授权由该成员关系的 `appStoreRelease` 单独控制；产品运营和管理员按其角色具备渠道能力。更新同一成员关系时，显式 `false` 撤销授权，省略该字段保留原值。执行时重新检查权限；撤权不会取消外部已经提交的任务。页面准入、产品线成员、应用服务与动作授权需分别满足，旧 API 的认证兼容边界见[架构文档](平台架构.md)。

Apple API Key 文件保留 `AuthKey_<Key ID>.p8` 命名，Key ID 从文件名识别；TestFlight 测试组通过 Apple API 获取。保存产品线配置时仅在 Podx 已启用的条件下同步对应工程配置。

## 3. Crash 与日志诊断

<a id="crash-diagnostics"></a>

### 3.1 dSYM 和本地符号化

**输入：**Crash/IPS 内容或日志文件，对应主应用/组件的 dSYM，可选版本/UUID。**输出：**符号化调用栈、缺失/匹配警告、历史记录、可选 AI 原因分析与报告。

推荐流程：先从构建同步或上传 dSYM → 核对 UUID/架构/版本 → 提交日志符号化 → 查看未还原帧及警告 → 补齐符号后重新处理 → 分析并保存/下载结果。

已有功能：

- dSYM 上传、从 xcarchive 导入、列表查询、下载、版本/备注维护与删除。
- `.crash`、`.ips` 识别，多 dSYM 处理，系统符号辅助与符号化缓存。
- 版本自动识别、AI 分析、历史按版本查询、重新分析和修复标记。
- 报告下载及企业微信结果分享。

当前 `SymbolizerService` 主链路使用 `atos` 和 `dwarfdump`，IPS 先转换。缺少正确 UUID 的 dSYM 时，版本名称相同也不能保证准确还原；AI 解释不能替代符号匹配结果。

接口分组：`/api/dsym`、`/api/symbolicate`、`/api/history`、`/api/config`、`/api/cleanup`、`/api/wechat`。符号与报告的操作细节见下文。源码：[symbolicate.routes.ts](../backend/src/routes/symbolicate.routes.ts)、[history.routes.ts](../backend/src/routes/history.routes.ts)。

#### 符号核对、缓存与历史

从对应 Xcode Archive、Jenkins 归档或组件交付源取得 dSYM，使用 `dwarfdump --uuid "/absolute/path/MyApp.app.dSYM"` 对比原始日志的 Binary Images、架构和构建。组件关联版本用于筛选，不能替代 UUID 一致性检查。

第三方摘要缺少 UUID、镜像加载地址或架构时，手选符号不能补造地址映射，应取得完整原始日志。从 Bugly 导出文件供本地处理不代表平台已接通 Bugly 数据 API。系统帧另按[系统符号配置](部署与运行.md#system-symbols)补齐。

`POST /api/symbolicate` 使用 `crashLog`、`uuid` / `uuids`；`saveHistory` 缺省保存，显式 `false` 不保存。内存缓存按产品线、原始日志和排序后的 UUID 列表区分，上限 100 条、24 小时过期，重启清空；SQLite 历史独立持久化。补齐符号后结果仍旧，可按接口权限调用 `POST /api/symbolicate/clear-cache` 清理当前产品线缓存再试。

| API | 操作 |
| --- | --- |
| `POST /api/dsym/upload`、`POST /api/dsym/upload-from-xcarchive` | 上传符号或导入 Archive |
| `GET /api/dsym/list`、`PUT /api/dsym/:uuid` | 查询、维护版本/备注 |
| `POST /api/symbolicate/analyze` | 分析当前日志 |
| `GET /api/history/list`、`GET /api/history/:id` | 查询历史与详情 |
| `POST /api/history/:id/analyze`、`PATCH /api/history/:id/fixed` | 重新分析与维护修复标记 |

历史为空或缺表时先核对 `DB_PATH`、当前上下文和初始化日志；迁移由启动过程处理，不使用旧手工建表步骤。

#### 下载与分享

`POST /api/symbolicate/download` 和 `GET /api/history/:id/download` 返回包含原始日志、符号化文本及 HTML 分析的 ZIP。页面分享将包含 `/history?id=...` 的文本复制到剪贴板，由用户粘贴到企业微信；复制成功不代表已发送。

后端仍保留独立的 `/api/wechat/share`、`/config`、`/test`，使用产品线 Corp ID、Agent ID、Secret，详情地址由 `BASE_URL` 配置。这与页面复制和 Jenkins Webhook 通知是三条不同路径。接收者仍需网络访问和相应产品线/应用权限。

排障优先级：应用帧看 UUID/架构/加载地址 → 部分模块看缺失组件 dSYM → 系统帧看 DeviceSupport → 结果未变化看缓存 → 分享空记录看 historyId、登录和上下文。AI 原因解释与历史修复标记都不能替代真实修复验证。

实现依据：[符号缓存](../backend/src/services/SymbolicationCacheService.ts)、[报告生成](../backend/src/services/ReportGeneratorService.ts)、[页面分享](../frontend/src/utils/wechatShare.ts)、[企业微信 API](../backend/src/routes/wechat.routes.ts)。

### 3.2 Sentry 与 Crash 治理

**输入：**查询条件、版本、Issue、UID/DeviceID 或原始 Crash。**输出：**问题列表、原始事件、符号化历史、AI 分析、治理状态、风险与覆盖信息。

已有功能：问题同步、单项/批量符号化、单项/聚合分析、原始日志查看，治理看板、问题/指纹状态修改、事件查询与导出、版本/问题覆盖刷新。AI 支持按用户/设备查崩溃、比较版本和跨系统诊断。

需启用当前 iOS 应用的 Sentry，并配置产品线的地址、组织、项目和凭据。切换到未适配数据接口的提供商后，不能用旧 Sentry 数据的空风险结果证明当前提供商健康。

主要接口：`/api/sentry-analysis/issues`、`/api/sentry-analysis/governance/*`；原站页面通过 Sentry 同源代理访问。

### 3.3 反馈日志、实时日志和水印

| 场景 | 操作和结果 | 依赖 |
| --- | --- | --- |
| 反馈日志 | 按用户/上下文查询日志，读取/预览日志或分析压缩包，结合业务语义定位时间与事件 | OP 和反馈日志源；`/api/feedback-log/*` |
| 查询记录 | 批量保存用户查询记录、备注、管理历史 | `/api/user-query-records` |
| 实时日志 | 创建配对会话，通过配对标识和 Token 将 App 日志推送到浏览器 | `/api/pairing/*`、`/ws/logs`、`/logs/view`；客户端需支持对应配对协议 |
| 水印诊断 | 上传图片交给 Rust 解码工具解析 | `/api/watermark/decode`；需启用水印服务和构建解码器 |

实时日志与黑盒 UI 回放的接入要求不同：UI 回放依赖 WDA，实时日志还要求客户端配对协议。不能认为所有 App 无需接入就能推送业务日志。

## 4. 组件库与 Git 工程管理

**入口：**组件库 `/pods`，以及对应 Git/分支管理操作。**主要人员：**研发维护组件，管理员维护凭据与跨仓库操作配置。

已有能力包括组件名/版本查询、包上传发布、失败重试、版本替换、podspec 修改、分支同步、删除前检查与删除、官方组件版本/依赖查询和导入。NNRTC 支持关联 Jenkins 构建、发布/替换任务及 dSYM 回填；IM SDK 有单独的版本与发布适配。

Git API 提供仓库配置、分支查询、Pod 依赖解析、分支任务预检和流式执行。DevOps 技能库展示 Podx/mgit 等命令及安装脚本，不是可以执行任意 Shell 的 Web 终端。

组件发布结果同时涉及组件数据库、二进制仓库和 Specs/Git；应检查任务结果及目标版本，不能只看上传成功。共享组件库的变更可影响多个绑定产品线。

接口：`/api/pods/*`、`/api/git/*`。源码：[pods.routes.ts](../backend/src/routes/pods.routes.ts)、[git.routes.ts](../backend/src/routes/git.routes.ts)、[DevOpsPage.tsx](../frontend/src/pages/DevOpsPage.tsx)。

### 4.1 共用组件库的使用规则

每个应用绑定一个同系统组件库，同库可被多个产品线复用；目前没有 Android Maven 实现。库的来源产品线管理 Nexus/Specs 凭据，应用主仓库、Job 与源码协作配置保持独立。来源产品线被禁用后，该库不可用，不会静默回退到另一产品线资源。

共享版本禁止覆盖或删除，修正应发布新版本；前述替换/删除能力仍受此规则限制。切换绑定不合并旧记录，也不会自动向工程师推送配置；已经运行的发布任务固定使用提交时的组件库。

工程师更新 `podx.config.yml` 后，按工作流使用 `podx --create-overlay-file`、`podx doctor`、`podx install --no-repo-update` 和 `mgit status` 检查覆盖文件、依赖及仓库状态。平台发布成功后还需确认目标版本和 Specs/Nexus 的一致性。

## 5. 构建、发布与 Apple 设备

### 5.1 iOS 构建和发布

**入口：**`/cicd`。**输入：**分支、渠道、版本、按规则要求的门禁源构建及发布说明。**输出：**Jenkins 队列/构建记录、发布单阶段、包和渠道状态。

常见流程：

1. 查询分支和已有构建，查看日志、构建失败分析、包体积及符号状态。
2. 普通开发测试包走 Pgyer 构建；Apple 渠道选择 TestFlight 或 App Store。
3. 发布前运行预检，核对分支/版本、源构建、质量门禁和渠道阻断项。
4. 按渠道权限提交构建/发布，持续跟踪 Jenkins 与发布单阶段。
5. 查看实际分发/审核结果；需要时进行提审、撤审或停止构建等独立操作。

测试与研发可使用测试发布能力；产品运营可发布 App Store；研发发布 App Store 需要当前产品线的单独授权；管理员维护发布配置。具体动作还受服务端预检和验证密码规则约束。

主要接口：

| API | 用途 |
| --- | --- |
| `GET /api/jenkins/nn/branches`、`GET /api/jenkins/nn/builds` | 分支和构建 |
| `GET /api/jenkins/nn/builds/:number/log` | 构建日志 |
| `GET /api/jenkins/nn/builds/:number/package-size` | 包体积分析 |
| `POST /api/jenkins/nn/builds/:number/sync-dsyms` | 构建符号同步 |
| `POST /api/jenkins/nn/release/preflight` | 发布预检 |
| `POST /api/jenkins/nn/release-gate/preview` | Jenkins 发布门禁预览 |
| `POST /api/jenkins/nn/build` | 提交构建/发布 |
| `POST /api/jenkins/nn/builds/:number/submit-app-store-review` | 提交商店审核 |
| `POST /api/jenkins/nn/builds/:number/cancel-app-store-review` | 撤销商店审核 |

API 返回队列成功只表示请求已提交；发布完成应以构建、产物和渠道结果为依据。

### 5.2 Apple 设备登记

**入口：**`/cicd/devices`。用户创建登记会话，在 iPhone 上打开/扫码并安装描述文件，回调采集 UDID 后生成申请；管理员查询、审批并登记 Apple 开发者设备。也有直接查找/登记接口。

管理员配置 Apple API Key、设备查询等资源；公开描述文件回调按已签发登记会话处理，不依赖扫码浏览器当前选择的应用。设备登记不等于安装 App，也不等于质检设备已经完成 WDA 配对。

接口：`/api/apple-devices/status`、`/enrollments`、`/enroll/:id/*`、`/registration-requests`、`/devices`、`/register`（后几项均以 `/api/apple-devices` 为前缀）。

## 6. iOS 自动质检与回放

### 6.1 标准质检

**入口：**`/cicd/quality`。**前置条件：**Jenkins、质检 Job、可用设备池和设备执行环境已配置。

选择源构建/包、套件和设备 → 发起任务 → 查看准备/安装/执行/采集阶段 → 打开质量报告 → 查看失败 Issue 和原始证据 → 必要时重跑或停止。

| 套件 | 当前职责 | 不能直接推出的结论 |
| --- | --- | --- |
| Smoke | 基础安装/启动与基础质量验证 | 全业务流程通过 |
| Monkey | 随机与业务感知探索，稳定性、页面停留和 Crash 现场采集 | FPS、帧级卡顿或完整业务覆盖通过 |
| Stutter | 场景操作耗时、性能采样和 xctrace 等证据 | 所有设备/所有场景性能达标 |
| Business flow | 按业务流程预设执行并输出结果 | 网页回放资产的不可变发布版本已接入 Jenkins |

安装模式区分开发/Pgyer 包与已安装的 TestFlight/App Store 包；后者可跳过安装，要求设备上的包和 Bundle ID 与测试目标一致。

报告可能包含 `summary.json`、`result.json`、`issues.json`、HTML 报告、设备日志、Crash/IPS、截图与性能文件，具体取决于套件和采集成功情况。后端结合 Jenkins 状态、本地进度和总结文件修正状态；应以本次运行的证据判断结论。

接口：`POST/GET /api/quality/tasks`、`GET /api/quality/tasks/:taskId`、`GET /api/quality/tasks/:taskId/issues`、`POST .../rerun`、`POST .../cancel`，以及 `/api/jenkins/nn/quality/*` 的设备池/报告管理。

设备分配以 UDID 为依据，多设备需独立 WDA 端口和 DerivedData，不能只按展示名称调度。任务进度还可来自 `quality-progress.json`；报告中缺失的采集项不能按通过处理。标准 Jenkins 质检与平台直接 WDA 回放是两条执行路径。

业务感知 Monkey 使用 `config/nnios-business-map.json` 和 `config/nnios-business-flow-presets.json`（以及对应产品线配置），覆盖 login、im、community、voice_room、profile、playwith 等领域，并区分允许、需守护和禁止动作。套件/API 名称不证明完整登录、IM、RTC 测试已经实现；精确卡顿分析使用独立 Stutter 套件。执行环境与归档设置见[iOS 真机和质检部署](部署与运行.md#ios-quality-setup)。

<a id="replay-flows"></a>

### 6.2 真机录制与流程资产

**入口：**真机调试台和回放中心。**输入：**选定设备、WDA 页面状态、用户操作及运行输入。**输出：**录制、流程草稿、节点执行结果、截图和 XML 证据。

使用顺序：

1. 连接 USB 设备，确认画面流、截图和页面 source 可读取。
2. 开始录制，通过调试台执行点击、滑动和输入；录制包含动作前后证据，也可采集观察记录。
3. 停止录制，确认纳入回放的步骤；观察记录需按界面支持的方式整理/提升为步骤，不能把观察本身等同于确定性输入事件。
4. 预览录制来源并创建流程，使用现有步骤/画布/低代码投影调整目标、等待、条件、断言和失败分支；计划中的安全 YAML 编辑器与语义往返验收仍待完成。
5. 保存草稿并校验；可配置前置/后置流程，完成创建后执行，查看阶段和节点证据。
6. 维护资产名称、来源变化，按需从录制重置、复制、归档或恢复。

执行边界：语义定位优先、坐标兜底；重试和超时有限；不提供任意脚本和无限循环。组合前置失败后主流程跳过，后置仍尝试执行；终止和失败在运行记录中区分。运行输入值不写入公开运行 JSON，但这不意味着截图/XML 中的页面内容已自动全面脱敏。

当前执行的是校验通过的草稿。数据库虽保留版本结构，仍缺少可验证的“发布不可变版本 → 正式质量任务绑定版本”链路；历史运行记录不保存完整 DSL，不能将其称为完整版本审计快照。

主要接口：`/api/device-control/recordings*`、`/replay-flow-assets*`、`/replay-flows/validate`、`/replay-flows/runs*`、`/replay-flow-chain-runs*`（均以 `/api/device-control` 为前缀）。

源码：[deviceControl.routes.ts](../backend/src/routes/deviceControl.routes.ts)、[ReplayFlowDesigner.tsx](../frontend/src/components/ReplayFlowDesigner.tsx)。设计目标见[回放编排需求](设计与演进.md#replay-design)，其中规划应与上述现状区分。

<a id="android-delivery"></a>

## 7. Android 首期交付

**入口：**选择 Android 应用后进入 `/android`。**前置条件：**Android 仓库、包名、构建 Variant、APK 路径、Jenkins Build Job；启用质检时另配 Smoke Job 和指定 adb 序列号。

1. 查看 readiness 的配置缺项。
2. 输入完整 Commit 创建 APK 构建，跟踪并同步原运行。
3. 构建证据通过后，基于该运行创建 Smoke。
4. 查看包哈希、版本、设备及日志/截图证据，处理失败 Issue。
5. 门禁通过后按权限下载内部 APK。

平台对请求键、源运行、Commit、APK SHA-256、包信息与 Smoke 证据进行关联校验。提交不明先同步原运行，不用新请求键反复触发。Issue 解决须引用有效 Smoke 运行，不能只凭人工切换状态证明已修复。

当前仅为 APK 与指定设备安装启动验证：不支持 AAB、商店发布、R8/NDK 符号、性能分析或完整业务回归。真实产品与外部 Jenkins/设备验收状态仍为待验证。

接口：`GET /api/android/readiness`、`GET/POST /api/android/runs`、`POST /api/android/runs/:id/sync`、`POST .../cancel`、`GET .../gate`、`GET .../download`、`GET /api/android/issues`、`POST /api/android/issues/:id/resolve`。

### 7.1 身份、同步与门禁

构建要求完整 40 位 Commit 和幂等请求键，运行先持久化再派发。提交结果不明标记为 `dispatch_unknown`；恢复查询目标 Job 最近 100 个构建及当前队列，按 `PLATFORM_REQUEST_ID` 精确匹配。记录被删除、重复命中或仍不明确时需人工对账，不能换新请求键盲重试。运行保存 Jenkins 基地址快照，下载不跟随外部重定向。

下载需构建清单、实际 APK、同源最新 Smoke 及问题状态共同满足门禁；解决问题需同一 APK 的后续成功 Smoke，无未解决 Crash/ANR。Android 门禁独立于 iOS Workflow readiness，不以 iOS 证据替代 Android 验证。Smoke 仅观察启动后约 10 秒，既不是完整 Crash/ANR 监控，也不证明业务回归覆盖。

平台超过 45 分钟仍保留同步/取消入口；Job 超时和产物大小限制见[Android Runner 部署与契约](部署与运行.md#android-runner)。真实接入验收须走“配置 → 固定 Commit 构建 → 归档核验 → 指定设备 Smoke → 门禁下载”，并验证失败阻断、幂等恢复和同 APK 问题闭环。

## 8. 质量中心与交付诊断

**入口：**`/workflow`，当前页面仅对管理员开放。它汇总已有证据，并提供问题处理与验证入口。

| 页签 | 输入与操作 | 输出/含义 |
| --- | --- | --- |
| 交付诊断 | 输入 Jenkins 源构建号 | 六阶段证据、缺口、优先动作；依据同步快照 |
| 平台概览 | 查看统一产物、任务和关联信息 | 研发与质量实体概览 |
| Issue 中心 | 查询/更新状态、查看详情、生成修复建议或回归候选 | 统一问题与处理入口；状态关闭不等于回归通过 |
| 变更影响 | 提交变更上下文，分析模块/依赖 | 风险与测试建议；需启用 Podx |
| 发布门禁 | 指定构建、版本和策略进行评估 | 阻断/警告/通过及证据；预览与保存评估分开 |
| 回归候选 | 从 Issue 生成候选，生成/导出/验证/运行 XCUITest | 代码、编译或 Runner 结果；不同阶段不能混为执行成功 |
| 知识与发布观察 | 沉淀知识、记录评测反馈、录入版本指标和查看健康 | 发布观察与知识记录；尚未证明自动完成整轮发布后观测 |

交付诊断有以下限制：只读当前同步数据；证据超限会标记不完整；回归候选 `verified` 尚不能证明覆盖本次构建；发布观察按版本聚合；正式发布仍由 Jenkins 发布服务实时复核。

运维 API 还提供同步状态、手动同步、存储统计、数据库备份、保留策略和压缩。部分是 API 能力，不应推定都有独立前端管理页。

核心接口：`GET /api/workflow/delivery/:buildNumber`、`/overview`、`/artifacts`、`/tasks`、`/issues`、`/relations`、`/events`、`/release-gates/*`、`/regression-candidates/*`、`/knowledge/*`、`/ai-evaluations`、`/release-observations`、`/release-health/:releaseVersion`、`/operations/*`（均以 `/api/workflow` 为前缀）。

XCUITest 的生成、导出、独立模拟器 SDK 类型检查与实际 Runner 执行是不同阶段。导出文件位于数据目录的 `workflow-xcuitest/exports`，实际执行由 `WORKFLOW_XCUITEST_RUNNER_URL` 指向的 CI/临时工作区 Runner 承担，可配置 `WORKFLOW_XCUITEST_RUNNER_TOKEN`。生成与导出不向 App 源工程自动注入文件；建议代码不能当作已修复或已验证结果。

后续证据绑定与效果衡量见[设计与演进](设计与演进.md#platform-evolution)。

## 9. 首页 AI 会话执行

AI 是已有服务的受控入口，通过注册工具查询事实、组织诊断、提出执行动作和跟踪结果。明确意图可能直接匹配规则，不一定每次调用模型。

| 任务类别 | 例子 | 对应能力 |
| --- | --- | --- |
| 故障诊断 | 查询某 UID 的最近反馈日志；查某 DeviceID 的崩溃 | 日志/Sentry 查询、跨系统诊断 |
| Crash 分析 | 比较两个版本；检查缺少哪些 dSYM；分析已上传 IPS | 版本对比、符号诊断、附件符号化和历史分析 |
| 构建 | 打 develop 测试包；分析构建失败；跟踪某构建 | Jenkins 构建、失败分析和状态验证 |
| 质检 | 查看质量日报；为构建发起测试；查询失败 Issue | 创建/跟踪/重试任务及回归候选 |
| 交付 | 诊断源构建就绪情况；检查门禁与发布健康 | Workflow 诊断工具，当前主要为管理员能力 |
| 工程知识 | 搜索接口、路由、跨端调用；分析组件升级影响 | 能力目录、API/路由检索、Pod 影响 |
| Android | 检查接入缺项；固定 Commit 构建；同步 Smoke 与门禁 | Android 专属工具 |

交互规则：

- 页面展示操作预览和工具结果；普通执行一次确认，高风险发布/停止两次确认。
- 角色不足、服务已关闭或平台不匹配时，不开放相应工具；确认时重新校验，旧确认不能绕过停用状态。
- 发布验证密码在最终确认表单输入，不通过普通聊天交给模型。
- 工具参数经过 Schema 白名单；模型没有任意 URL、Shell、SQL 或隐藏接口执行权限。
- AI 待确认动作有效期为 15 分钟；服务重启后不能依靠旧待确认对象续执行。
- 页面聊天刷新后清空，工具调用保留审计，部分语义分析信息会写文件。附件限制 10 MiB，仅 `.crash/.ips/.txt`，15 分钟过期并在后续附件访问/注册时清理。

接口：`GET /api/assistant/capabilities`、`POST /api/assistant/turn`、`POST /api/assistant/actions/:id/decision`、`POST .../cancel`、`GET .../status`、`POST /api/assistant/attachments`；会话和确认结果使用 SSE。

管理员可从 AI 提效看板及 `/api/assistant/audits`、`/semantic/stats`、`/datasets/capabilities/*` 查看审计、意图解析和能力数据集。已有使用统计不等于已经测得实际研发耗时减少或修复正确率。
