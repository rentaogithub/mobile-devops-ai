# AI 驱动移动研发平台：评审与演进方案

评审日期：2026-09-07。范围：当前仓库、测试基线及服务配置指向的 SQLite 只读汇总。外部 Jenkins、真机、Sentry 实时状态与模型线上效果未在本轮重新验收。

## 核心判断

平台已经具备研发服务基础，主要短板是证据进入平台后没有稳定转化为可验证的处理结果。下一阶段以交付闭环为核心：每次构建关联变更与产物，每个问题关联责任人与验证，每次 AI 建议关联实际采纳结果，每次发布关联观察窗口。

AI 的职责是理解意图、组织证据、解释风险、提出行动和复用经验；执行结果、权限、发布条件由确定性服务校验。复杂诊断使用高能力模型，查询、状态判断和明确意图走已有工具，按实测效果决定模型路由。当前任务本机配置为 `gpt-6-astra` / `high`；平台服务端模型仍由自身配置控制，本轮没有修改平台模型或发送真实业务数据进行模型评测。

## 现状与证据

已存在的服务链路：

| 链路 | 已有实现 | 主要缺口 |
| --- | --- | --- |
| 需求与变更 | Git、Pods、ChangeImpactService | 缺少需求/验收项到变更的统一引用；变更影响推荐尚未统一转为执行计划 |
| 构建与产物 | Jenkins、WorkflowIntegrationService、产物与关系表 | 部分质量任务缺 Commit；消费方仍需拼接上下文 |
| 质量执行 | 标准质检、真机回放、不可变流程版本、Crash 证据 | 测试结果与当前源构建的证明不够完整；通用门禁曾遗漏非必需套件失败计数 |
| 问题处理 | Issue 中心、AI 修复建议、负责人字段 | 缺少稳定认领与处理流程；修复建议未关联修复 Commit/PR 和验证构建 |
| 回归沉淀 | 回归候选、XCUITest 生成/编译/Runner | 数据使用尚未形成闭环；verified 不能直接证明覆盖本次构建 |
| 发布与观察 | 发布门禁、分级确认、实名审计、Crash 治理、版本观察 | 无观测时曾可能判健康；观察窗口、样本量、指标完整度仍待制度化 |
| AI 提效 | 工具注册、确定性意图识别、跨系统诊断、评测记录 | 模型/规则实际来源、成本、采纳与后续验证需要贯通 |
| 运行保障 | 定时同步、在线备份、保留策略、健康检查 | 同步新鲜度、失败补偿与恢复演练应成为交付证据的一部分 |

## 本轮已落地

1. 新增“质量中心 → 交付诊断”，输入 Jenkins 源构建号，返回变更与产物、构建、质量验证、问题处理、回归闭环、发布观察六个阶段，以及排序后的行动入口。
2. 新增 `GET /api/workflow/delivery/:buildNumber` 和 `workflow_delivery_readiness` AI 工具，共用 `DeliveryReadinessService`。明确中文意图可直接调用工具，不需要模型请求。
3. 对当前产品线按构建查询；Issue 在后续构建复现时仍通过关系表保留旧构建引用。单类证据超过 500 条明确标记不完整，不能获得整体通过结论。诊断不写 Workflow 数据、不调外部执行接口。
4. 缺少构建状态不再默认成功；源构建已知 Commit 时，缺少 Commit 的必需测试不能通过；缺少发布观察且无已知风险时返回 `unknown`；已知高风险仍保留阻断/警告。
5. 测试选择以执行尝试时间优先，避免同步旧任务覆盖后续任务。非必需套件中的 Crash/失败用例也参与门禁阈值。
6. 发布诊断与 Jenkins 发布复用必需套件配置解析。切换产品线重新挂载质量中心，清除旧结果；请求失败清除上一次诊断，避免显示旧结论。

诊断输出是规则驱动的证据汇总，AI 可以使用同一结果解释和组织下一步工作。本轮没有把缺失链路伪装成自动闭环。

## 分阶段演进

以下为后续工作，不是已完成能力。按阶段验收后推进，周期需要结合团队资源确认。

### P0：证据可信、问题可处理

- 为质量任务建立强制源构建标识、Commit、产物校验值、流程版本、执行时间与证据引用；遗留缺失项进入补齐队列。门禁拒绝错误或无法证明来源的测试。
- 把同步状态纳入诊断：来源、最近成功时间、游标、失败原因、重试次数；增加幂等补偿和死信处理，避免查询页面顺带同步成为唯一保障。
- 对 416 个开放 Issue 做来源/指纹/版本核对，分配负责人、模块与目标修复版本；保留误报与忽略理由，不批量假关闭。
- 统一服务端权限入口，清点旧 Workflow 写接口与 `AUTH_ENABLED` 兼容路径；针对真实角色矩阵验证，不把“已有实名审批”解释为所有接口均完成权限治理。

建议验收：新质检任务的源构建/Commit/证据关联完整率 100%；每个阻断问题有负责人和处理状态；同步故障可发现、可重放；无证据路径不得通过门禁。

### P1：变更驱动验证，问题驱动回归

- 引入 Delivery/Change 上下文，连接需求与验收项、Base/Head Commit、构建与产物、测试计划和发布单。
- 变更影响分析输出版本化测试计划：每个套件写明触发原因、风险覆盖、环境、预计耗时和完成条件。复用现有队列，显式处理取消、超时、幂等与重试。
- Issue 增加修复引用（Commit/PR）与验证运行；“修复完成”与“已验证”分开，只有同一修复构建的验证证据可以闭环。
- AI 提出修复计划、补充候选回归；代码修改先落隔离工作区/草稿 PR，经验证和评审后合入。执行权限继续由现有服务控制。

建议验收：选一个高频业务域完成“变更 → 构建 → 风险测试 → Issue → 修复引用 → 同构建回归”的真实样本；记录人工步骤数、诊断耗时和回归稳定性，与现有流程对照。

### P2：发布观察与 AI 效果闭环

- 发布时创建观察任务：明确版本、构建、渠道、观察窗口、最低样本量与指标集合。过期、样本不足、缺指标返回未知；持续高风险进入明确处理队列。
- 关联回归逃逸、Crash-free sessions、启动、核心流程成功率和性能回退，形成发布前后对照。
- 记录 AI 的实际模型/规则来源、Prompt 版本、证据引用、时延、token/成本、人工采纳以及后续是否验证通过。规则回退不得记成模型成功。
- 从已验证的处理过程生成知识候选，标明适用产品、版本和失效条件。检索引用有出处；知识采纳后仍须验证。

建议验收：至少一个版本完成受控发布与规定窗口观察；至少一组真实案例完成模型/Prompt 对照评测；没有人工或自动结果标签时不展示虚假的采纳率。

## 衡量“高效高质”

| 目标 | 指标与口径 |
| --- | --- |
| 交付效率 | Commit 到验证构建可用的 P50/P95 时长；诊断到确定责任人的时长；单次交付人工操作数 |
| 验证质量 | 新任务血缘完整率；必需风险场景覆盖率；重跑后结果反转比例；发布后逃逸问题数 |
| 问题闭环 | 负责人覆盖率；同修复构建验证率；重新打开率；长期无人处理数量 |
| AI 效果 | 有标签样本的采纳率、采纳后验证通过率、诊断证据引用正确率、每个有效结果成本 |
| 平台可靠性 | 同步延迟 P95、积压与失败补偿耗时、关键服务可用性、备份恢复演练结果 |

先采集一个完整迭代周期作为基线，再设改善目标。没有分母和采样窗口的百分比不用于宣称提效。

## 验证与边界

- 改动前：前后端类型检查通过，后端 24 个套件 / 158 项测试、前端 2 项测试通过。
- 改动后：`npm run check` 通过，后端 25 个套件 / 172 项测试、前端 2 项测试通过；前后端构建通过。前端仍有既有的大体积 chunk 告警，代码分包属于后续性能优化。
- 浏览器验收：运行本地 Vite 服务后执行 `node scripts/test-delivery-readiness-ui.mjs`，覆盖入参校验、证据展示、处理入口、失败刷新、产品线切换；所有 API 使用固定测试数据，不代表外部集成已验收。
- 本轮覆盖：无源构建、规则门禁、非必需套件失败、旧任务同步、同号构建产品线隔离、Issue 重现血缘、只读性、截断、回归验证语义、HTTP 入参、AI 意图与工具权限。
- 诊断依赖已同步数据，正式发布仍由 Jenkins 实时复核。发布观察按版本聚合，尚不证明某一渠道/构建已达到观察窗口。
- 不新增数据库表，不清理存量数据，不触发真实打包、真机测试、发布或消息发送；不自动创建 Commit/PR。
