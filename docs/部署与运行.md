# 移动管理平台部署与运行

按 2026-09-08 当前代码整理。整体组件关系见[架构文档](平台架构.md)，业务入口见[功能文档](平台功能.md)。下面是部署步骤，不表示当前环境已经执行或验收。

## 1. 运行环境

| 环境 | 要求 |
| --- | --- |
| Node.js | 使用仓库 `.node-version` / `.nvmrc` 指定的 22.22.3；根 npm 包装器选择 Node 22 |
| npm | 支持 workspaces；在仓库根目录统一安装依赖 |
| 平台宿主机 | 本地符号化及 iOS 真机能力依赖 macOS、Xcode/设备工具 |
| Rust / Cargo | 后端构建会先编译水印解码器 |
| screen | 使用 `start-platform.sh` 后台运行开发服务时需要 |
| Android Agent | 使用 Android 能力时另配 JDK、Gradle/Android SDK、Python、adb |
| 外部服务 | Jenkins、Sentry、Apple 等按应用已选服务配置 |

不要仅升级 Node 而继续复用旧 ABI 的 SQLite 原生模块。运行时检查和原生依赖处理由 [run-with-supported-node.mjs](../scripts/run-with-supported-node.mjs) 与 [ensure-native-deps.mjs](../scripts/ensure-native-deps.mjs) 提供。

## 2. 安装与环境配置

在仓库根目录、Node 22 环境中执行：

```bash
npm install
```

创建或编辑 `backend/.env`。已有部署保留原配置，以下路径和密码均为需要替换的示例：

```dotenv
PORT=3000
DATA_DIR=/absolute/path/nn-ios-platform-data
DB_PATH=/absolute/path/nn-ios-platform-data/database.sqlite
UPLOAD_DIR=/absolute/path/nn-ios-platform-data/uploads
DSYM_DIR=/absolute/path/nn-ios-platform-data/dsyms
DEVICE_RECORDING_DIR=/absolute/path/nn-ios-platform-data/device-recordings
DEVICE_REPLAY_RUN_DIR=/absolute/path/nn-ios-platform-data/device-replay-runs
REPLAY_FLOW_CHAIN_RUN_DIR=/absolute/path/nn-ios-platform-data/replay-flow-chain-runs

AUTH_ENABLED=true
ADMIN_USERNAME=admin
ADMIN_DISPLAY_NAME=平台管理员
ADMIN_PASSWORD=replace-with-a-strong-admin-password
AUTH_PASSWORD=replace-with-a-separate-legacy-password
AUTH_SESSION_TTL_HOURS=12
```

使用绝对数据路径，避免从不同工作目录启动时创建第二套数据库或上传目录。`DATA_DIR` 不会自动覆盖其他路径配置。

首次启动在用户表为空且配置了管理员密码时创建实名管理员；已有用户不会因修改环境变量自动重建或重置密码。账号和产品线成员通过“配置管理”维护。旧密码中间件与实名会话仍并存，`AUTH_ENABLED=true` 不能代替逐路由权限核验，边界见[架构文档](平台架构.md)。

后端 [env.ts](../backend/src/config/env.ts) 以 `override: true` 加载找到的环境文件；不能假定命令行同名变量一定覆盖 `.env`。

### 可选 AI 配置

```dotenv
OPENAI_API_KEY=replace-with-your-service-key
OPENAI_API_ENDPOINT=https://api.openai.com/v1
OPENAI_MODEL=replace-with-your-enabled-model
OPENAI_API_STYLE=responses
```

也支持 `chat_completions` 协议。密钥可通过平台配置管理，数据库配置优先级由配置服务决定；修改模型、地址或协议后重启后端。AI 能否使用具体工具还取决于角色、系统和服务选配。

### 外部业务服务

管理员按“产品线 → 应用 → 服务选配 → 资源配置”接入 Jenkins、Sentry、Podx、Apple 等。不要复制其他产品线的标识当作自己的配置。

业务配置见[应用与服务](平台功能.md#application-services)、[成员权限](平台功能.md#permissions)和[共享组件库](平台功能.md#shared-components)。Android、iOS 真机与系统符号环境统一见本指南后续章节。

## 3. 开发与日常后台运行

开发模式：

```bash
npm run dev
```

默认前端为 [localhost:5173](http://localhost:5173)，后端为 [localhost:3000](http://localhost:3000)。后端实际端口由 `PORT` 决定；Vite 可通过 `VITE_BACKEND_TARGET` / `BACKEND_TARGET` 指定后端，否则探测候选端口。

日常后台运行可使用脚本：

```bash
./start-platform.sh start
./start-platform.sh status
./start-platform.sh restart
./start-platform.sh stop
```

脚本用独立 screen 会话保持前后端运行，检查后端就绪后启动前端；输出到仓库根的 `backend-dev.log`、`frontend-dev.log`。它只处理当前平台所属进程，遇到其他程序占用端口会报错。该脚本仍运行开发服务，不等同于生产构建部署。

## 4. 构建与生产运行

在仓库根目录执行：

```bash
npm run check
npm run build
npm start
```

`build` 生成后端 `backend/dist` 和前端 `frontend/dist`，并编译 Rust 解码器、复制 SQL 和模板。后端发现前端构建产物后会提供静态文件和 SPA 回退，生产部署不需要同时启动 Vite。

`npm start` 使用根脚本设置的默认上传/符号/数据库路径，并加载 `backend/.env`；建议在该文件中明确绝对路径。单独执行后端 workspace 的 start 不会执行根脚本的全部原生依赖处理。

前置反向代理应将页面和 API 转发给后端，并满足：

- 保留 Host 与转发协议，配置 HTTPS 后使用生产模式和安全 Cookie。
- 支持 `/ws/logs` WebSocket Upgrade。
- 对 AI SSE 和设备画面流关闭响应缓冲，设置适当读超时。
- 若代理全站，请保留 Sentry、OP 和 Apple 描述文件回调路径。
- 上传体积限制与后端接口一致，不只配置 JSON 请求上限。

`NODE_ENV=production` 时会话 Cookie 默认启用 Secure；仅通过 HTTP 访问时浏览器不会正常使用这种 Cookie。实际 TLS、代理地址和进程托管方式由部署环境确定。

## 5. 健康、数据与恢复

| 入口 | 说明 |
| --- | --- |
| `GET /health/live` | 进程存活 |
| `GET /health/ready`、`GET /health` | SQLite 查询及数据库文件可访问性 |
| `GET /api/health/dependencies` | 依赖状态；需正确应用上下文，不是所有依赖的完整功能验收 |
| `GET /api/workflow/operations/sync` | 当前产品线周期同步状态 |
| `GET /api/workflow/operations/storage` | 存储与保留策略预览 |

缺省行为：iOS 数据源每 10 分钟同步；数据库每 24 小时备份；WAL 每 6 小时 checkpoint；上传临时文件每小时清理，默认保留 24 小时。相关环境变量和删除开关见[架构文档](平台架构.md)。

数据库在线备份使用 SQLite backup API，可由 `POST /api/workflow/operations/backup` 触发；这只是数据库副本，不包含 dSYM、录制证据、发布单 JSON、Jenkins 归档。

迁移/恢复时，先停止平台写入，分别保存数据库备份和实际配置指向的持久资产；同步迁移所需外部归档、凭据配置与权限，恢复后核对路径、登录、代表性历史证据和健康状态。不要把仅复制运行中的主库文件作为完整备份。

历史表初始化及增量迁移由 `initializeDatabase()` 处理。缺表时先核对实际 `DB_PATH`、运行目录和启动日志，不先执行旧文档中的手写 SQL 或清空数据库。

## 6. 常见故障

| 现象 | 排查方向 |
| --- | --- |
| SQLite native module/ABI 错误 | 核对 Node 22，执行 `npm run ensure:native` 后再启动 |
| 前端代理连接失败 | 检查实际后端 PORT、健康接口及 Vite 代理目标 |
| 启动后历史数据为空 | 核对 DB_PATH 与产品线/应用选择，排除使用了另一套数据目录 |
| 登录后仍显示未登录 | 检查 Cookie、HTTP/HTTPS、代理协议、账号状态和产品线成员关系 |
| 菜单或 API 返回服务未启用 | 检查应用服务选配，资源地址齐全不等于服务已启用 |
| 系统帧仍是地址 | 核对 ENABLE_SYSTEM_SYMBOLICATION 与匹配版本的 DeviceSupport |
| Jenkins/WDA 不可用 | 分别检查外部服务、执行用户、设备配对和 Xcode，不用平台 ready 代替执行验收 |

本指南不包含真实环境验收结果。部署脚本和 Jenkins 运维 Job 说明另见 [scripts/README.md](../scripts/README.md)。

## 7. iOS 系统符号

应用和组件使用自己的 dSYM；UIKit、Foundation 等系统帧需要对应 iOS 系统符号。应用符号化流程见 [Crash 诊断指南](平台功能.md#crash-diagnostics)。

依据：[SystemSymbolsService.ts](../backend/src/services/SystemSymbolsService.ts)。本文不预设当前机器的符号目录是否存在或已有任何版本。

### 启用与目录

在 `backend/.env` 中配置：

```dotenv
ENABLE_SYSTEM_SYMBOLICATION=true
XCODE_SYMBOLS_PATH=~/Library/Developer/Xcode/iOS DeviceSupport
AUTO_UPDATE_SYSTEM_SYMBOLS=true
```

只有 `ENABLE_SYSTEM_SYMBOLICATION=true` 才开启系统符号化；路径缺省为当前运行用户的 Xcode DeviceSupport 目录。代码会展开这里的 `~`。`AUTO_UPDATE_SYSTEM_SYMBOLS` 缺省开启，但仍需已有基础目录和可用导入来源。

在实际运行后端的 macOS 用户下检查：

```bash
xcode-select -p
ls -ld "$HOME/Library/Developer/Xcode/iOS DeviceSupport"
ls "$HOME/Library/Developer/Xcode/iOS DeviceSupport"
```

如果目录缺失，先创建：

```bash
mkdir -p "$HOME/Library/Developer/Xcode/iOS DeviceSupport"
```

目录存在只证明路径可访问，不代表包含可还原系统帧的符号。

### 获取符号

可以连接对应 iOS 真机，通过 Xcode 的 Devices and Simulators 完成设备支持准备，检查是否生成所需符号；也可从已有完整符号的 Mac 或团队维护的符号源复制。不同 Xcode/iOS 组合的产物不同，不能保证连接设备后一定下载到可用系统符号。

使用与日志中的 iOS 版本和 build 对应的目录，内部需包含可用的 Symbols 文件，例如：

```text
iPhone15,2 26.5 (23F77)/
└── Symbols/
    ├── System/
    └── usr/
```

这是结构示例，不表示当前环境已安装此版本。

### 自动补齐来源

按需要配置：

```dotenv
IOS_DEVICE_SUPPORT_IMPORT_DIR=/absolute/path/ios-device-support-packages
IOS_DEVICE_SUPPORT_URLS=https://symbols.example.com/device-support.zip
IOS_DEVICE_SUPPORT_URL_TEMPLATE=https://symbols.example.com/{encodedVersionDir}.zip
```

查找匹配版本失败时，服务依次尝试本地导入目录、显式 URL 列表和模板 URL。`IOS_DEVICE_SUPPORT_URLS` 使用逗号分隔；模板支持 `version`、`build`、`versionDir` 及对应的 `encoded*` 变量。

本地源可以放置版本目录或 ZIP。未配置来源、导入失败或缺少系统库时，查看后端日志，先保留已能恢复的应用/组件调用栈，不将部分符号化描述为全部还原。

### 验证与排障

1. 核对运行用户、启用开关和目录权限，确认服务读到的是预期 DeviceSupport 路径。
2. 从原始日志读取 iOS 版本/build，检查对应目录中的系统二进制是否齐全。
3. 配置或符号变更后重启后端；重新处理代表性日志，检查目标系统帧与警告。
4. 当前实现先匹配版本，失败后可能搜索其他版本；得到函数名仍需核对符号来源，不能将跨版本兜底当作准确匹配证明。
5. 系统符号不能替代主应用/组件 dSYM；主应用帧异常时按 UUID 和构建来源排查。

`scripts/download-symbols.sh` 是辅助脚本；准备符号前应核对自己的环境，不要依赖历史文档中“已下载”“目录为空”等机器快照。


<a id="ios-quality-setup"></a>

## 8. iOS 真机与 Jenkins

### 真机与标准质检

在实际执行任务的 macOS 用户下准备兼容的 Xcode、签名团队、开发者模式与 USB 信任配对，安装 libimobiledevice / ideviceinstaller、Python/tidevice 等对应脚本依赖。可通过 `idevice_id -l`、`tidevice list` 核对设备识别；再独立确认 WDA 能启动、截图和 Source 可读取。设备签名、锁屏或 WDA 故障不会因平台 `/health/ready` 成功而消失。

设备池记录真实 UDID；多设备分别分配 WDA 端口和 DerivedData。安装来源区分开发/Pgyer 包与跳过安装的 TestFlight/App Store，后者必须确认已安装目标 Bundle ID 与包版本。

Jenkins 标准质检 Job（默认约定 `nn-auto-quality`）调用 [ios-quality.sh](../scripts/ios/ios-quality.sh)，参数以脚本与平台生成值为准：

| 参数组 | 主要参数 |
| --- | --- |
| 构建来源 | `SOURCE_JOB`、`SOURCE_BUILD_NUMBER`、`BRANCH`、`COMMIT_HASH`、`APP_VERSION` |
| 安装来源 | `PACKAGE_URL`、`ARCHIVE_URL` |
| 套件与设备池 | `TEST_SUITE`、`DEVICE_POOL`、`DEVICE_POOL_LABEL`、`DEVICE_CLOUD` |

归档 `quality-results/**`，按实际生成内容发布 `quality-results/**/*.xml` JUnit。保留 summary/result/issues、HTML、进度、截图、录像、日志、Crash/IPS 和性能采集文件；归档存在不代表所有采集项成功。业务配置与套件边界见[自动质检功能](平台功能.md#ios-quality)。

### 本机执行环境准备与验收

质检和回放使用显式 `WDA_PROJECT_PATH` 或 Appium 安装的 WebDriverAgent。设备池可在平台管理，也可用 `QUALITY_DEVICE_POOLS_JSON` 初始化；设备使用 UDID，不使用外部设备分组 ID。

```bash
bash scripts/ios/setup-monkey-runtime.sh
bash scripts/ios/pair-and-launch-ios.sh <UDID> <Bundle-ID>
```

第一条脚本准备 Node/Appium/XCUITest Driver，随后在 Xcode 中核对 WDA 签名与开发者团队。iOS 17+ 性能采样需要 root 常驻隧道时，按执行机要求运行 `scripts/ios/install-pymobiledevice3-tunneld-launchdaemon.sh` 做一次性配置。

Jenkins 模板为 `scripts/jenkins/nn-auto-quality-config.xml`，执行入口为 `scripts/ios/ios-quality.sh`；现有 Job 可通过平台“同步质检 Job”或 `scripts/jenkins/sync-nn-auto-quality-job.sh` 更新。旧 Job 的脚本入口保留转发兼容。

验收顺序：Mac 识别真机 → WDA 启动、截图和 Source → 平台设备池 → Jenkins 收到源构建与 UDID → 代表性套件产出报告和证据。对 WDA、安装和采集失败分别排查。

## 9. Android Runner 与产物契约

### 执行环境

使用 [构建 Pipeline](../scripts/android/Jenkinsfile.build)、[Smoke Pipeline](../scripts/android/Jenkinsfile.smoke) 和 [runner.py](../scripts/android/runner.py)。Agent 标签约定 `android-build` / `android-device`；安装 Python 3.9+、项目兼容的 JDK、Android SDK、apkanalyzer、apksigner，仓库提供 `gradlew`，Smoke 节点另有 adb 与已授权的固定设备。

把经过审核、固定版本的 Runner 放在被测仓库之外，用绝对路径 `PLATFORM_ANDROID_RUNNER` 指定。仓库凭据由 `ANDROID_GIT_CREDENTIALS_ID` 配置，签名走 Jenkins/Gradle 的凭据配置。平台访问 Jenkins 使用 API Token；运行记录固定提交时的 Jenkins 基地址。

Smoke Job 依赖 Copy Artifact 和 Lockable Resources 插件，复制指定源构建 APK 并按 adb serial 加设备锁。构建/Smoke 默认超时 30/15 分钟，归档默认保留 50 次；平台 APK 下载上限 512 MiB，单项证据上限 20 MiB。需要长期追溯时同时维护 Jenkins 保留策略，SQLite 备份不包含这些归档。

### 归档契约

| 归档文件 | 必须关联的内容 |
| --- | --- |
| `mobile-delivery.json` | `schemaVersion=1`、`kind=build`、`requestId`、`applicationId`、`packageId`、完整 `commit`、`apkPath`、`sha256`、字符串 `versionCode`/`versionName` |
| 实际 APK | 与构建清单路径、包标识、版本及 SHA-256 一致 |
| `mobile-quality.json` | 相同身份字段、`sourceRunId`/`sourceJob`/`sourceBuild`、APK SHA-256、实际安装包名/版本、`deviceSerial`、启动/Crash/ANR 布尔结果 |
| Smoke 证据 | `evidence` 与 `evidenceSha256` 对应的 logcat、screenshot、packageDump，逐项归档并校验 |

Smoke 安装后核验实际安装 APK 哈希并观察启动约 10 秒。清单缺字段、设备不符、证据缺失或哈希不匹配不能通过门禁。派发不明确、幂等恢复与同 APK Issue 闭环见[Android 使用规则](平台功能.md#android-delivery)。

首条真实产品验收需准备仓库、完整 Commit、两个 Job 和指定设备，核对实际构建/归档/安装/Smoke/门禁下载，补充失败与恢复验证。离线适配完成不等于外部 Jenkins/真机已经通过。

## 10. Workflow 执行与运维补充

回归候选生成和导出使用平台能力；实际 XCUITest 执行需配置 `WORKFLOW_XCUITEST_RUNNER_URL`，按部署要求配置 `WORKFLOW_XCUITEST_RUNNER_TOKEN`。Runner 在 CI/临时工作区执行，单独检查构建环境、鉴权、结果回写和证据访问。平台导出目录为数据目录下的 `workflow-xcuitest/exports`。

部署后先核对同步状态与代表性源构建证据，再验证门禁和 Runner；类型检查通过不能代替真机运行。文件、数据库和外部归档的备份恢复边界仍遵循第 5 节。
